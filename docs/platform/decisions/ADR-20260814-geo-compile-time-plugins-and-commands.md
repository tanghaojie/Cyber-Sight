# ADR-20260814：Geo 编译期插件与统一命令架构

## 背景

维护者希望把早期 Cesium 启动模板升级为更插件化、现代化且可接入 AI 的 Geo 业务能力。旧项目将
Cesium 实例作为应用级全局能力，适合演示和单用途应用，但 Cyber-Sight 需要可审查的业务模块边界、
稳定的场景持久化以及与权限体系一致的 AI 操作入口。

## 决策驱动因素

- 隔离 Viewer、图层、工具和事件处理器的生命周期；
- 允许后续增加新的图层、工具和分析能力而不持续扩大工作区页面；
- 保持静态构建、类型检查、供应链审阅和上游同步可控；
- 让 UI、快捷操作和 AI 使用同一套业务命令与校验；
- 避免在只有一个业务用例时建立远程插件平台或跨领域 Agent 框架。

## 考虑的方案

1. 继续使用全局 Cesium 实例并由页面直接操作：实现最快，但生命周期、测试和功能耦合会继续扩大。
2. 支持运行时远程插件：扩展性最强，但引入代码信任、版本、沙箱、签名、供应链和发布兼容问题。
3. 使用随应用构建的编译期内置插件，并以类型化命令目录统一 UI 与 AI 操作：扩展边界清楚，风险与首版需求匹配。

## 决策

采用方案 3。

- `geo` 是单一 Platform 业务模块，插件是模块内部的编译期能力贡献单元；
- 插件通过稳定 ID、版本、贡献类型和幂等销毁函数登记，不加载远程代码；
- 首版扩展点限于图层适配器、交互工具和类型化命令；出现真实需求后才能增加新扩展点；
- Cesium Viewer 由单一非响应式适配器拥有，插件获得受限上下文，不共享可变全局对象；
- 页面按钮、快捷入口和 AI 都通过 `GeoCommand` 执行，不直接调用其他插件内部实现；
- 命令声明运行时输入 Schema 和副作用等级，AI 对非纯视图命令只生成待确认提案；
- Geo 核心能力不依赖模型可用，模型端口先保留在 Geo 内部，第二个业务用例出现后再评估提取。

## 正面结果

- 插件能力、场景状态和 Cesium 资源生命周期可以单独推理和迁移；
- 新功能必须通过明确贡献点进入工作区，减少页面和 store 之间的隐式耦合；
- AI 不获得任意代码或 Cesium API 执行权，权限和输入校验可以复用正常路径；
- 所有插件代码继续经过仓库构建、审阅、依赖锁定和发布流程；
- Geo 可以先交付核心能力，未来再按证据扩展插件和 AI 基础设施。

## 负面结果与风险

- 新插件仍需要修改仓库、构建和发布，不能由终端用户即时安装；
- 命令与插件 manifest 增加初始结构成本，过度设计会产生空扩展点；
- 插件配置进入持久化后，稳定 ID、版本和迁移成为长期兼容责任；
- 如果未来确实需要第三方插件市场，必须另行解决签名、沙箱、权限、依赖和兼容协议，不能把当前接口直接当作公共远程插件 ABI。

## 验证和复审条件

- 至少通过图层、绘制和测量三类真实能力验证插件生命周期；
- 场景恢复时未知插件不会阻止其他插件加载，也不会丢弃原始配置；
- Viewer 重建和路由离开后无重复事件处理器、DataSource 或 Primitive；
- UI 与 AI 对同一命令使用相同的 Schema、权限和执行器；
- 如果出现跨仓库第三方插件、无需重新构建的安装需求，或 Market 形成第二套成熟命令/AI 用例，重新评审本决策。
