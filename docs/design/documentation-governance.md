# 文档治理设计

## 目标

让后续参与项目的人和 AI 能回答三个问题：系统为什么这样设计、某次改动计划怎样执行、人与 AI 当时确认了什么。

## 信息分层

- `design/` 保存当前有效设计，允许原地更新。
- `decisions/` 保存重要取舍及原因，不用修改历史来掩盖决策变化。
- `plans/` 保存一次具体工作的执行步骤和验证结果。
- `ai-logs/` 保存协作上下文摘要，帮助解释计划和决策如何形成。

同一内容不应在多个位置完整复制。正式结论放在设计或 ADR，计划和日志通过链接引用它。

## 文档生命周期

```text
用户目标或问题
  -> 在首次修改前确认 Git 暂存区为空
  -> 更新设计草案
  -> 必要时新增 ADR
  -> 创建 active plan
  -> 建立 AI log
  -> 实施并持续记录偏差
  -> 验证代码与文档
  -> plan 移入 archive
  -> 提交已验证改动并写入 AI 模型 trailer
```

设计文档没有“完成归档”状态，因为它必须持续描述当前系统。计划必须有明确状态：`draft`、`active`、`completed`、`cancelled` 或 `superseded`。

## 沟通记录边界

AI 日志不是完整聊天转储，而是面向未来维护者的结构化记录，包括：

- 用户目标和明确约束。
- 关键问答与已确认决定。
- AI 做出的重要假设。
- 方案变化、实施结果和验证证据。
- 未解决问题及下一步。

敏感信息、无关闲聊、冗长的工具输出和可由 Git 直接获得的逐行修改不写入日志。

## 强制方式

`AGENTS.md` 作为仓库级 AI 指令，规定 Git 安全门禁、非简单任务的文档门禁和 AI 提交标记，并要求每次验证通过后提交本轮完整改动。代码评审时也应检查文档是否同步。未来引入 CI 后，应增加自动检查：涉及 API、模块或数据模型的改动必须同时修改对应设计、计划和测试。

### Git 暂存区门禁

每次 AI 执行可能修改代码或仓库文件的任务时，必须在首次修改前使用 `git diff --cached --quiet` 确认索引相对 `HEAD` 没有差异。若任务开始时已有暂存内容，AI 必须停工并要求人类先提交；AI 不得代交、取消暂存、还原或删除这些内容。人类提交后，AI 必须重新检查，只有暂存区为空才能继续。

这项检查用于隔离人类尚未提交的工作与 AI 即将产生的工作。它不禁止 AI 在本轮实现和验证完成后暂存自己的改动以创建最终提交。

### AI 提交标记

AI 创建的所有提交必须在消息末尾保留一个空行，并追加以下 Git trailer：

```text
Co-Authored-By: -AI- [AI model name] <ai@scaffold-proj.com>
```

提交时必须把 `[AI model name]` 替换为实际执行提交的模型名称，不得保留占位符或猜测模型身份。提交完成后必须读取最新提交消息，确认 trailer 正确存在。该规则也适用于仅包含文档、配置或测试的 AI 提交。
