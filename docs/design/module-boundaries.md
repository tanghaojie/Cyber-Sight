# 模块边界

## 组织原则

业务能力是主要组织单元。前端、后端和契约使用一致的稳定模块名；没有某一层实现时不创建空目录。

```text
apps/frontend/src/modules/<module>/
apps/backend/src/modules/<module>/
packages/api-contract/src/modules/<module>/
```

页面、状态、用例、领域规则、仓储适配器和业务 Schema 由所属模块拥有。组合根只注册路由、插件和依赖；`shared` 只放领域无关的平台能力，不能成为业务代码兜底目录。

## 公共文件

模块用表意文件公开稳定能力，例如 `<module>.routes.ts`、`<module>.store.ts`、`<module>.api.ts`、`<module>.schema.ts`、`view-registry.ts`。对应模块设计必须登记允许外部依赖的文件和符号；未登记文件都是内部实现。

禁止模块级 `index.ts` 或同类无差别 barrel。包发布入口、框架固定入口等例外必须在设计中说明。其他模块不得：

- 穿透导入页面、私有状态、仓储、数据库实现或内部 Schema；
- 直接读写其他模块的 store、表或仓储；
- 通过根级 barrel 隐藏真实依赖；
- 用动态导入、全局单例或路径别名掩盖循环依赖。

## 依赖与数据所有权

```text
应用组合根
    -> 业务模块公共文件
        -> 领域无关 shared / 平台能力
```

依赖必须单向、显式且无循环。跨模块协作使用目标模块公开的查询/命令、共享契约、消费方端口或领域事件。每份业务数据只有一个所有者；跨模块事务、共享表或双向同步必须另写设计，说明一致性和失败恢复。

典型模块内部数据流是：

```text
传输层 -> 应用层 -> 领域规则 -> 基础设施适配器
```

小模块可以合并层次，但 Vue 页面和 Fastify 路由不能长期承载全部业务规则。

## 变更门禁

新增模块或实质修改存量模块时确认：

1. 职责、非目标、数据所有者和模块名明确。
2. 公共文件最小、表意且已在模块设计登记。
3. 依赖单向，无跨模块深层导入和循环。
4. 单元测试覆盖模块规则，集成测试覆盖公共协作。
5. 删除模块时，可枚举组装点和明确依赖方。

存量代码在功能增加、模型变化或跨模块数据流调整时迁移本次触及部分；纯缺陷修复可以最小改动，但不得扩大耦合。后续静态边界工具只能执行本设计，不能反向定义架构。

## 失败模式

- `shared` 业务化：确定所有者并恢复公共接口。
- 表意文件退化为 barrel：让调用方依赖真正承担职责的文件。
- 跨模块直连数据库：改用所有者接口并在边界鉴权、校验。
- 伪模块目录：以实际所有权和依赖判断，不以目录名称判断。

长期入口命名规则见 [ADR-0013](../decisions/ADR-0013-semantic-module-entry-files.md)。各模块的具体公共文件见[模块设计索引](README.md)。
