# ADR-0037：独立静态应用发布开源推广站

## 背景

仓库需要一个面向潜在使用者和贡献者的公开推广页。管理端是需要后端与数据库的产品应用壳，不适合直接作为 GitHub Pages 静态站发布；README 又缺少沉浸式界面展示和适合传播的网页元数据。

## 决策驱动因素

- GitHub Pages 只能托管静态产物。
- 推广内容不应依赖管理端登录态、私有组件或后端可用性。
- 站点需要与现有 Vue/TypeScript 工具链一致，并纳入根工作区验证。
- 页面需要支持中英文、三维展示和无障碍降级，同时保持较小依赖面。

## 考虑的方案

1. 把推广页加入 `apps/frontend`：可复用组件，但会把公开站与管理端路由、认证和部署耦合。
2. 在仓库根维护手写 HTML/CSS：依赖最小，但中英文内容、复杂交互和类型约束较弱。
3. 新增独立 Vite + Vue 静态应用：与现有栈一致、边界清晰，可单独构建并发布。

## 决策

采用方案三，在 `forge/website` 创建独立 Vite + Vue 3 应用，通过 GitHub Actions 发布其 `dist` 到 GitHub Pages。站点不跨应用导入管理端内部文件；品牌 SVG 可以在站点公共资产中保留一份发布副本，并由品牌设计文档约束一致性。

运行时中英文切换由站点本地内容资源和浏览器存储实现，语言入口固定放在 Header。三维轮播只使用 CSS transform 和原生滚动进度，不增加 WebGL 或动画运行时依赖。

## 正面结果

- 推广站可以独立演进、预览、发布和回滚。
- 不增加后端或生产数据库暴露面。
- GitHub Pages 子路径和管理端部署方式互不影响。
- 页面依旧共享仓库格式、Lint、TypeScript 和构建门禁。

## 负面结果与风险

- 品牌图标存在发布副本，需要在品牌变更时同步检查。
- 中英文文案会增加静态资源和维护成本。
- GitHub Actions 成为新的外部部署依赖，仓库设置不正确时发布会失败。

## 验证和复审条件

首次部署后检查 Pages URL、静态资源、锚点和分享元数据。如果推广站需要内容管理、动态案例或与管理端共享大量运行时代码，重新评估独立静态应用边界。
