# 模块边界与独立目录

## 背景与目标

项目会持续增加前端页面、后端用例、API 契约和数据访问代码。若只按 `views`、`routes`、`services`、`stores`、`db` 等技术类型平铺文件，一个业务改动会散落在多个公共目录中，模块所有权不清晰，也容易产生深层导入、循环依赖和隐式数据库耦合。

本设计把业务能力作为主要组织单元。每个模块具有独立目录、明确登记的公共文件和可验证的依赖边界，使新增、替换或删除一个模块时，对无关模块的影响保持可控。

## 范围与非目标

本设计适用于 `apps/frontend`、`apps/backend`、`packages/api-contract` 以及未来承载业务能力的 workspace。

它不要求：

- 每个模块都是独立 npm 包、进程或微服务。
- 为不存在实现的层创建空目录。
- 在一次文档任务中重排全部存量代码。
- 禁止模块之间协作；协作必须经过显式公共接口。

## 模块识别

满足以下任一条件的代码应作为独立模块：

- 表达一个可命名的业务能力或业务域，如 `auth`、`users`、`orders`。
- 拥有独立生命周期、权限、数据所有权或失败模式。
- 可以由一个小组独立开发和测试，或未来可能被替换、关闭、拆分。

纯格式化函数、通用 HTTP Client、日志、配置加载和数据库连接等领域无关能力属于共享平台代码，不必伪装成业务模块。`shared` 只能承载跨业务、稳定、领域无关的能力，不能作为暂时无法归类代码的兜底目录。

## 职责与边界

### 目录边界

同一业务能力在各 workspace 使用相同的稳定模块名：

```text
apps/frontend/src/modules/<module>/
apps/backend/src/modules/<module>/
packages/api-contract/src/modules/<module>/
```

一个模块的页面、组件、状态、用例、领域规则、仓储适配器和业务 Schema 必须由该模块目录拥有。根级技术目录只保留应用组装、平台设施或真正跨模块的代码。

建议结构如下，目录按实际复杂度创建，不要求保留空层：

```text
apps/frontend/src/modules/<module>/
├── <module>.routes.ts
├── <module>.store.ts
├── <module>.api.ts
├── pages/
├── components/
├── composables/
└── tests/

apps/backend/src/modules/<module>/
├── <module>.routes.ts
├── <module>.service.ts
├── transport/
├── application/
├── domain/
├── infrastructure/
└── tests/

packages/api-contract/src/modules/<module>/
├── <module>.schema.ts
└── <module>.types.ts
```

以上文件按实际职责创建，不要求模块补齐所有示例文件。小模块可以在模块目录内合并文件，但不能省略独立模块目录，也不能把业务规则永久留在应用组装、Vue 页面或 Fastify 路由中。

### 公共接口

模块使用能说明职责的文件名直接暴露稳定能力，例如 `<module>.routes.ts`、`<module>.store.ts`、`<module>.api.ts`、`view-registry.ts` 或更具体的用例名。模块设计文档必须登记允许外部依赖的公共文件及其符号；未登记文件一律视为内部实现。

避免使用 `index.ts` 或把多个无关能力聚合成 barrel。只有第三方工具要求固定入口、包发布入口等无法用表意文件替代的情况才保留 `index.ts`，并在所属设计文档说明原因。公共文件只导出外部调用所需的稳定类型、注册函数、应用服务、事件和组件；内部仓储实现、数据库 Schema、私有状态和辅助函数不得导出。

其他模块必须通过目标模块已登记的公共文件导入，禁止：

- 使用相对路径或别名穿透到另一个模块的内部文件。
- 直接读取或修改另一个模块的 Pinia store、领域对象内部状态或仓储。
- 绕过模块接口直接访问由另一个模块拥有的数据表或业务 Schema。
- 通过根级 barrel 文件重新导出所有模块内部实现，掩盖真实依赖。

应用组合根可以从模块已登记的路由、注册或服务文件导入并完成路由、插件和依赖注入。模块不得反向依赖组合根。

### 依赖关系

允许的默认依赖方向是：

```text
应用组合根
    |
    v
业务模块公共文件 ---> 其他业务模块公共文件
    |
    v
领域无关 shared / 平台能力
```

依赖必须单向、显式且无循环。跨模块协作优先使用以下方式：

- 共享契约中的公共请求、响应和事件类型。
- 目标模块公开的应用服务或查询接口。
- 由消费方定义、在组合根注入实现的端口接口。
- 对无需同步返回结果的流程使用显式领域事件。

发现循环依赖时，不得用路径别名、动态导入或全局单例掩盖。应重新划分职责、反转依赖，或经设计评审提取具有独立语义的新模块。

## 公共接口

模块设计文档必须列出公共文件及其导出的符号或接口类别。公共接口变更属于模块边界变更；影响其他模块时必须更新设计、调用方测试和实施计划。

前端路由、后端模块注册和契约包出口都是组合点，只能从模块已登记的公共文件导入。包级发布入口可以显式重新导出各模块公共 API，但不得导出其内部文件；包内模块目录不因此增加 `index.ts`。

## 数据模型与数据流

每份业务数据都必须有明确的所有者模块。所有者负责其业务 Schema、校验、状态变化和持久化规则。

典型请求数据流为：

```text
模块契约 Schema
    |
    v
模块传输层 -> 模块应用层 -> 模块领域层
                              |
                              v
                       模块基础设施适配器
```

其他模块需要数据时，通过所有者公开的查询/命令接口或事件副本获取，不能直接复用其仓储或表访问代码。跨模块事务、共享表和双向同步属于例外，必须先形成专门设计并说明一致性、失败恢复和所有权。

## 依赖治理与变更检查

新增模块或实质修改存量模块时，设计和评审至少确认：

1. 模块名、职责和非目标是否清晰。
2. 所有业务文件是否位于独立模块目录。
3. 公共文件是否表意、最小且稳定，是否存在未登记的跨模块导入。
4. 依赖方向是否单向，是否形成循环。
5. 数据所有者和跨模块数据流是否明确。
6. 单元测试是否在模块边界内，集成测试是否覆盖公共协作。
7. 删除该模块时，需要修改的组装点和依赖方是否可枚举。

当前先以设计审查、代码评审、搜索和测试执行该门禁。静态依赖检查工具可在后续计划中引入，但工具缺失不降低本约束的效力。

## 失败模式与安全考虑

- **共享目录业务化**：多个模块通过 `shared` 隐式共享业务状态。处理方式是明确所有者并恢复公共接口。
- **公共文件膨胀**：模块导出内部实现导致调用方绑定实现细节。处理方式是按职责拆分表意文件并提供面向用例的接口。
- **表意文件退化为 barrel**：文件名虽然不叫 `index.ts`，却仍无差别转发模块内部实现。处理方式是让调用方直接依赖承担职责的文件，并删除无业务语义的转发层。
- **循环依赖**：模块无法独立测试或删除。处理方式是反转依赖、使用事件或重新划分能力。
- **绕过数据所有权**：调用方直接读写其他模块表，导致权限、审计和不变量失效。必须通过所有者接口，并在边界执行鉴权和校验。
- **伪独立目录**：虽然存在模块文件夹，但业务仍主要散落在根级页面、路由和仓储中。评审以所有权和依赖为准，不以目录名称为准。

## 测试与验证策略

- 模块领域规则和应用服务使用不依赖其他模块内部实现的单元测试。
- 模块公共文件至少有类型检查或导入测试，避免调用方依赖未登记的内部文件。
- 跨模块流程使用集成测试，依赖方通过公共接口或测试替身交互。
- 架构审查通过搜索跨模块深层路径、循环引用和业务代码进入 `shared` 的情况验证边界。
- 后续引入静态检查时，应把本设计作为规则来源，而不是由工具默认配置反向定义架构。

## 兼容性与迁移

从本决策生效起：

- 新模块必须直接采用独立目录和表意公共文件，不创建默认 `index.ts`。
- 对存量模块做功能增加、数据模型变化或跨模块数据流调整前，必须先把本次触及的业务代码收敛到模块目录。
- 对存量 `index.ts` 在模块被触及时优先迁移；迁移调用方后删除无工具约束的 barrel。
- 纯缺陷修复可保持最小改动，但不得新增深层导入、循环依赖或扩大根级技术目录中的业务代码。
- 大范围存量迁移应单独建立设计与计划，逐模块完成，避免一次性移动造成不可审查的改动。

## 未决问题

- 是否使用 ESLint `no-restricted-imports`、dependency-cruiser 或 workspace 边界工具自动检查依赖。
- 管理系统现有 `admin` 聚合模块是否应按用户、角色、菜单和字典进一步拆分，需结合下一次业务演进评估。
