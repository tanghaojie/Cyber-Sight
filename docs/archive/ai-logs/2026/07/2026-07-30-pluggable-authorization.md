# 可插拔授权与部门实施协作

## 用户目标和约束

用户要求实现可插拔的细粒度接口权限和数据权限，并同步重构用户、角色和部门。接口权限保持轻量且与菜单权限一致；数据权限从用户、角色和部门获取与继承。讨论阶段不修改代码，用户确认设计和推荐默认决策后授权开始实施。

## 关键问答与确认

- 用户确认公共资源不需要 `owner_user_id` 或 `department_id`；业务表只登记真实归属维度。
- 用户确认一个主部门加多个附属部门、多角色 allow 并集、可选部门向下继承、无角色继承、第一版无 deny、按资源和动作配置、本地 Provider 默认且 Cerbos 可选。
- 角色通常作为授权来源，不要求所有业务表保存 `role_id`；确有角色业务归属时再使用语义明确的字段或关联表。

## AI 的重要假设

- 当前任务包含后端、共享契约、迁移和对应前端管理能力，而不仅是后端内核。
- 第一批数据范围应用到 `users` 资源；菜单、角色、字典和部门目录作为无行级归属的管理资源只做功能权限。
- `role_menus` 在迁移后保留兼容数据但退出运行时读写。

## 方案和执行摘要

完成暂存区门禁、现行设计和代码复核后，创建授权/部门设计、ADR-0025 和实施计划。共享契约新增权限目录、数据资源、三类主体策略和部门/用户归属；数据库新增权限、角色权限、部门闭包、用户部门和数据策略表，并回填默认部门、菜单权限、存量角色权限及超级管理员全量授权。

后端实现可注入的 `AuthorizationProvider`、默认本地 Provider、路由声明门禁、主体授权管理 API 和部门模块。跨模块查询通过 `users.access.ts`、`roles.access.ts`、`departments.access.ts` 与 `authorization.references.ts` 暴露。用户资源的列表/count/创建/更新/删除已接入按动作解析的数据范围；菜单改为按有效权限键生成导航，角色仓储停止读写 `role_menus`。

前端新增部门管理页面和复用的数据策略编辑器，用户支持主/附属部门及直接策略，角色支持功能权限与数据策略，部门支持可继承策略，菜单支持权限键。删除已退出使用的菜单授权选项适配器。

## 验证结果

- `pnpm format`、`pnpm format:check`、`pnpm lint`、`pnpm test`、`pnpm build` 全部通过。
- 后端 11 个测试文件、86 项测试全部通过；覆盖迁移、Schema、默认拒绝、allow 并集、all 短路、Provider 拒绝和路由声明门禁。
- PostgreSQL 18.4 连接检查通过，确认存量 `users` 与 Drizzle 迁移表存在；未自动执行迁移。
- 前端 TypeScript 与 Vite 生产构建通过；按仓库规则未创建或运行前端自动化/浏览器测试，维护者仍需人工验收。
