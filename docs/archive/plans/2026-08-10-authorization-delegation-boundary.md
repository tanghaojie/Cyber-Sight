# 授权委托边界完整修复

## 目标

修复授权主体配置和用户角色、部门归属变更中的无上限委托，使受限管理员不能读取或修改范围外主体，不能给自己或其他用户授予超过自身有效权限和数据范围的授权。

## 背景与设计依据

`users.manage` 原先只完成接口级功能门禁；`GET/PUT /admin/authorization/users/{id}` 没有调用用户数据范围，也没有校验待写入策略是否落在操作者可委托范围内。角色和部门授权配置存在相同的委托上限缺口，用户写入还可以分配任意有效角色或通过部门归属继承更高权限。

## 范围

- 在授权 Provider 边界增加主体访问配置和用户授权上下文的委托决策。
- 用户主体读取按 `users/read`、替换按 `users/update` 隐藏范围外目标。
- 当前配置和待写入配置都必须是操作者有效功能权限、用户记录范围和部门范围的子集。
- 用户创建或更新时，对角色、部门和直接策略形成的当前及目标授权上下文执行同一上限校验。
- 增加后端安全回归测试并同步授权、用户模块设计与 ADR。

## 非目标

- 不切换数据库主键类型。
- 不引入 deny、权限优先级、租户或通用 ACL。
- 不新增前端自动化测试；前端交互仍由维护者人工验收。

## 前置条件和风险

- 授权配置采用整体替换语义，拒绝越权请求时不得产生部分写入。
- 外部 `AuthorizationProvider` 必须实现新的委托决策接口；缺少实现不得默认放行。
- 动态部门范围必须按目标用户最终部门上下文计算；无法证明为子集时默认拒绝。

- [x] 编写可复现自提权与合法委托的失败测试。
- [x] 实现数据访问计划包含关系和策略委托校验。
- [x] 在主体授权路由应用目标范围与委托上限。
- [x] 在用户创建、更新应用角色和部门授权上下文上限。
- [x] 更新设计、ADR、验证记录并归档本计划。

- `pnpm --filter @cyber-ai-forge/backend test -- authorization-delegation.test.ts`：13 项通过；修复前首批同一测试因缺少委托决策而 5 项失败。
- `pnpm test`：API 契约构建校验通过，后端 15 个测试文件、139 项测试通过。
- `pnpm lint`：通过。
- `pnpm build`：API 契约、后端、前端和推广站生产构建通过；仅有既存 Sass 与 Rollup 警告。
- `pnpm format`、`pnpm format:check`、`git diff --check`：通过。
- `pnpm docs:archive:check:ci`：活动归档审查计划存在时返回 `IN_PROGRESS` 并通过门禁。
- 按仓库前端验证边界未创建或运行浏览器自动化测试。

## 发布与回滚

修复不改变数据库结构和 HTTP 请求结构。外部授权 Provider 需要与接口扩展同步发布；回滚必须整体回滚 Provider 接口、Controller 调用和测试，禁止只移除拒绝逻辑。

## 实际偏差和遗留问题

- 实施范围按完整攻击面扩展到用户、角色、部门主体配置，以及用户创建和更新中的角色、部门授权上下文，没有采用临时超级管理员白名单。
- 用户当前角色和部门在比较前按启用状态归一化，允许清理已经停用的旧归属，同时不削弱有效授权边界。
- 管理写入需要额外解析授权上下文；这是低频管理路径，当前未发现功能或安全阻塞。若单用户角色、部门数量未来显著增长，应以批量查询优化，不得放宽委托校验。
