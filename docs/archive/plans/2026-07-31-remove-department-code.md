# 移除部门编码

## 目标

从部门数据模型、部门管理接口与界面、部门选项和初始数据库基线中移除 `departmentCode`，仅使用部门 ID 处理层级、归属和数据策略关联。

## 背景与设计依据

用户确认不考虑外部系统对接。部门树由 `parentId` 与闭包表表达，用户归属和数据策略均引用 `departmentId`；部门编码不参与运行时业务判断，名称是唯一需要展示和搜索的部门信息。

## 范围

- 调整部门共享 Zod 契约、后端仓储、前端管理页面和部门选项。
- 从 `sys_departments`、初始迁移和 Drizzle 快照中删除 `code` 列及唯一索引。
- 更新部门和授权数据库设计文档与后端测试。

## 非目标

- 不改变部门树、用户主部门、数据策略或授权的 ID 关联语义。
- 不引入外部组织标识或替代编码。
- 不提供旧数据库原地升级；仓库当前仅维护面向空数据库的单一初始基线。

## 前置条件和风险

- 部门 API 结构为破坏性变更，全部前端调用方和测试必须在同一改动中迁移。
- 初始迁移不再以 `DEFAULT` 编码定位种子部门，改为在空数据库基线中按初始部门名称定位。

- `pnpm format`
- `pnpm test`
- `pnpm build`
- `pnpm lint`
- `pnpm format:check`
- 维护者人工验收：部门管理不再显示或要求编码；树搜索、父部门选择、用户部门选择和数据策略部门选择均按名称正常工作。

## 发布与回滚

该仓库当前只支持全新空数据库基线。发布时创建空 PostgreSQL 数据库并执行 `pnpm db:migrate`；回滚通过恢复上一版应用和匹配的空数据库基线完成。

## 实际偏差和遗留问题

已移除部门编码的数据库列、部分唯一索引、共享 API 字段、管理表单和列表列，以及树形搜索条件。初始基线仅在种子关联时按“默认部门”名称定位该记录；ID 仍是层级、归属和数据策略的唯一关系键。

`pnpm format`、`pnpm test`（100 项后端测试）、`pnpm build`、`pnpm lint` 和 `pnpm format:check` 均已通过。未运行数据库集成测试：没有可确认安全使用的空 PostgreSQL 数据库。前端自动化测试不在仓库维护范围；需由维护者人工验收部门新增/编辑、树搜索、上级部门选择、用户部门选择和数据策略部门选择。
