# 模块隔离与独立目录约束

## 目标

把“业务模块必须解耦并放在独立模块文件夹中”固化为仓库级强制规则，并为前端、后端和 API 契约提供可审查的目录、公共接口、依赖与测试边界。

## 背景与设计依据

现有系统概览已要求模块具有明确职责、公共接口和测试边界，但还没有规定统一的物理目录边界、跨模块引用方式和存量代码迁移规则。随着业务能力增加，仅依赖命名习惯容易产生深层导入、共享目录业务化和模块间循环依赖。

本次设计见 `docs/archive/design/module-boundaries.md`，长期决策记录于 ADR-0009。

## 范围

- 强化根目录 `AGENTS.md` 的模块架构约束。
- 新增系统级模块边界设计和 ADR。
- 同步系统概览、前后端/API 契约设计及维护者指南。
- 更新设计、ADR、计划和 AI 日志索引。

## 非目标

- 本次不重排现有业务源码。
- 本次不引入 Nx、dependency-cruiser 或 ESLint 边界插件。
- 本次不要求每个模块发布为独立 npm 包或独立部署服务。

## 前置条件和风险

- “独立模块文件夹”表示明确的代码所有权和公共入口，不等于禁止通过稳定接口协作。
- 现有前端 `views/`、`stores/` 和 API 契约入口仍有存量结构；采用“新增必须遵守、修改时迁移”的渐进策略。
- 没有自动化边界检查前，主要依赖设计审查、代码评审和测试，后续可单独立项增加静态检查。

- 审查 Git diff，确认没有修改业务源码或覆盖既有改动。

## 发布与回滚

本次仅修改仓库文档和 AI 开发规则，随 Git 提交生效。若约束不适用，通过新 ADR 调整决策，并同步设计文档和 `AGENTS.md`，不直接删除历史 ADR。

## 实际偏差和遗留问题

- 未修改业务源码，按计划只建立长期约束。
- 采用“新模块立即遵守、实质修改存量模块时迁移触及部分”的渐进策略，避免无业务需求的大规模目录重排。
- 当前未引入静态依赖边界工具；自动化检查作为后续可选任务保留。
- 文档链接、关键约束覆盖和 Git diff 检查通过。
