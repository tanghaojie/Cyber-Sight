# 统一软删除业务唯一性约束

## 用户目标和约束

菜单编码修复完成后，用户要求把其他表的同类软删除唯一性问题一起处理。

## 关键问答与确认

代码审查确认用户、角色仍使用全表唯一约束；字典和两个关联表把 `is_deleted` 放进联合
唯一索引，只允许一条同身份软删除历史。会话令牌哈希虽然也唯一，但属于不可复用安全
标识，不应放宽。

## AI 的重要假设

- 用户希望统一修复所有当前可复用业务身份，而非仅三个主业务表。
- 关联表应允许保留多条历史关系，但现有仓储仍可继续恢复已有行。
- 不改变 API、错误码或前端行为。

## 方案和执行摘要

新增 ADR-0015 取代 ADR-0014 的菜单局部范围。七个业务身份统一使用
`WHERE is_deleted = false` 部分唯一索引，`auth_sessions.token_hash` 保持全表唯一。

## 验证结果

- 生成并应用迁移 `0004_overconfident_dakota_north.sql`，删除三个全表业务唯一约束和
  三个包含 `is_deleted` 的旧联合索引，创建六个有效记录部分唯一索引。
- 加上已完成的菜单索引后，Schema 测试覆盖七个可复用业务身份；会话令牌测试确认仍为
  全表唯一。
- 后端 51 项、前端 29 项测试和 API 契约类型检查全部通过。
- API 契约、后端和前端生产构建全部通过，迁移生成确认无 Schema 漂移。
- PostgreSQL 回滚事务验证所有业务身份可经历两次软删除并继续复用，未删除重码仍返回
  `23505`；会话令牌软删除后复用仍返回 `23505`；未留下测试数据。

## 未决问题与下一步

本次范围内无未决问题。未来新增唯一字段时需先在模块设计中确定其是否为可复用业务身份。
