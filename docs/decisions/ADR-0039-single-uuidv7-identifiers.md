# ADR-0039：单一 UUIDv7 标识符与空库基线

## 背景

当前 17 张应用表都使用顺序 `serial` 主键，数字 ID 已贯穿数据库引用、共享 API 契约、JWT、授权数据计划和前端状态。顺序 ID 不是授权漏洞本身，但会降低批量枚举资源的成本。维护者明确不接受双 ID，并允许再次建立不兼容旧数据库的空库基线。

## 决策驱动因素

- 只维护一种实体标识，避免内部 ID、公开 ID 映射和排障负担。
- 保留数据库生成主键和 Drizzle 原生类型推导。
- 连续插入的系统表和接口日志需要合理的 B-tree 写入局部性。
- 根节点和系统操作者使用显式空值，不引入魔法 UUID。
- 迁移链应直接表达当前最终结构，不携带数字 ID 兼容历史。

## 考虑的方案

1. 保留数字主键并增加公开 UUID：兼容性好，但形成双 ID 和持续维护成本。
2. 全面使用 UUIDv4：兼容 PostgreSQL 版本更广，但随机主键的写入局部性较弱。
3. 要求 PostgreSQL 18，全面使用数据库生成的 UUIDv7，并重建空库基线。

## 决策

选择方案 3。所有应用表主键和实体引用统一为 UUIDv7；HTTP 和 TypeScript 使用 UUID 字符串。数据库是 ID 生成权威，运行环境最低版本提升为 PostgreSQL 18。

菜单与部门根节点从数字 `0` 改为 `null`；系统审计操作者从数字 `0` 改为 `null`。权限键、资源键等业务标识保持原有字符串。UUID 只降低标识枚举便利性，认证和授权仍是资源安全边界。

现行迁移链压缩为新的单一 `0000`，仅支持全新空库。旧数字数据库、旧 JWT 和旧前端缓存均不兼容，不提供双写、回填或兼容读取。

## 正面结果

- 数据库、API、JWT 和前端只存在一种实体 ID。
- UUIDv7 在保留高随机性的同时提供时间有序前缀，适合数据库主键写入。
- 删除数字根节点和系统操作者魔法值，空值语义更明确。
- 空库初始化直接得到最终 UUID 结构，无需执行过渡迁移。

## 负面结果与风险

- 这是全栈破坏性契约变化，旧客户端和旧数据库不能继续使用。
- UUID 索引和外键宽于 32 位整数，系统表与日志会增加存储开销。
- UUIDv7 暴露大致生成时间；它不适合作为机密信息。
- 部署环境必须提供 PostgreSQL 18，否则初始化直接失败。

## 验证和复审条件

- 新库迁移、数据库检查和自动化测试必须验证 PostgreSQL 18 与 UUIDv7。
- 若未来必须保留旧数据，单独设计离线 ETL，不恢复双 ID。
- 若 PostgreSQL 运行约束无法满足 18，复审生成方式，但不得在同一基线混用多种实体 ID 策略。
