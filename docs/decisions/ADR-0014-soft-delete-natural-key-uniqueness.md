# ADR-0014：软删除自然键使用部分唯一索引

本决策对菜单表的局部范围已由 [ADR-0015](ADR-0015-active-row-business-uniqueness.md)
扩展并取代；原始背景、取舍和菜单迁移记录保留用于历史追溯。

## 背景

`menus.code` 原先使用全表唯一约束。菜单软删除后记录仍在表中，再创建相同编码会触发
PostgreSQL 唯一约束，违反“软删除记录不可见且自然键可复用”的业务语义。

## 决策驱动因素

- 同一时刻只能存在一条未删除的同编码菜单。
- 软删除历史可以保留，且相同编码可以经历多次创建和软删除。
- 并发创建或更新时仍必须由数据库保证唯一性。
- 迁移不得删除或改写现有业务数据。

## 考虑的方案

1. 创建前由应用查询冲突：存在并发竞态，不能替代数据库约束。
2. 使用 `(code, is_deleted)` 联合唯一索引：只能保留一条同编码的已删除历史，
   第二次软删除会再次冲突。
3. 使用 `code` 上带 `WHERE is_deleted = false` 的部分唯一索引：只约束有效记录，
   同时允许任意数量的已删除历史。
4. 软删除时改写 `code`：污染审计历史，也会把持久化细节泄漏到业务行为。

## 决策

采用方案 3。菜单表删除 `menus_code_unique` 全表唯一约束，新增
`menus_code_active_unique` 部分唯一索引，条件固定为 `is_deleted = false`。

部分唯一索引属于 PostgreSQL 基础设施实现；业务语义仍表述为“菜单编码只在未删除记录
中唯一”。其他带软删除的自然键不随本次任务批量修改，应由各自模块按相同决策因素审查。

## 正面结果

- 软删除菜单后可以重新创建相同编码。
- 未删除菜单的编码冲突仍由数据库原子地拒绝。
- 可以保留多条同编码的软删除历史记录。

## 负面结果与风险

- 部分索引是 PostgreSQL 专属能力，迁移到其他数据库时需要等价实现。
- 应用必须继续把数据库唯一冲突转换为统一业务冲突响应。
- 现有数据库必须先删除旧唯一约束，再创建部分唯一索引。

## 验证和复审条件

Schema 测试校验索引的唯一性、列和条件；迁移 SQL 必须显式删除旧约束并创建新索引；
真实数据库验证覆盖删除后重建成功以及两个未删除菜单重码失败。更换数据库或引入恢复
已删除记录能力时复审。
