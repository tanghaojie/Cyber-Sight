# ADR-0009：以独立模块目录和公共入口隔离业务能力

## 背景

项目已有“模块化而非文件堆积”的原则，但尚未强制业务模块使用独立目录，也没有明确跨模块引用、数据所有权和存量迁移规则。随着页面、路由、服务、状态和数据库代码增加，按技术类型平铺会使一个业务能力散落在多个目录，并诱发深层导入、循环依赖和隐式共享。

## 决策驱动因素

- 业务模块能够独立开发、测试、替换和删除。
- 模块内部重构不应迫使无关模块同步修改。
- 前端、后端和契约能够以一致模块名表达同一能力。
- 依赖和数据所有权可在代码评审中识别。
- 存量项目能够渐进迁移，不以一次性目录重排制造风险。

## 考虑的方案

1. 继续按 `views`、`routes`、`services`、`stores`、`db` 等技术类型组织。初期简单，但业务所有权分散，模块演进时修改面持续扩大。
2. 每个业务模块都拆成独立 npm package。隔离最强，但会显著增加构建、版本、依赖和发布成本，当前规模没有必要。
3. 在每个现有 workspace 内使用独立模块目录和单一公共入口，以规则限制依赖，并在需要时再提升为独立 package。

## 决策

采用方案 3。

所有业务能力必须位于各 workspace 的 `src/modules/<module>/` 独立目录。同一能力跨前端、后端和 API 契约时使用一致模块名；缺少某一层实现时不创建空目录。

每个模块以 `index.ts` 作为默认唯一公共入口。其他模块只能通过公共入口依赖它，禁止深层导入内部页面、状态、仓储、数据库 Schema 和辅助实现。模块依赖必须单向、显式且无循环；跨模块数据访问必须经过所有者公开的服务、端口或事件。

`shared` 只承载领域无关的平台能力，不能存放无明确所有者的业务代码。应用组合根负责注册和注入模块，但不承载业务规则。

新模块立即执行。存量模块在发生功能增加、数据模型变化或跨模块数据流调整时迁移本次触及的部分；纯缺陷修复不得扩大现有耦合。完整规则见 `docs/design/module-boundaries.md`。

## 正面结果

- 目录结构直接表达业务所有权和模块边界。
- 调用方只依赖稳定入口，模块内部可以独立重构。
- 跨模块依赖、数据访问和循环引用更容易审查。
- 可逐步把复杂模块提升为独立 package，而无需提前承担全部工程成本。

## 负面结果与风险

- 小模块也需要一个目录和公共入口，文件数量会增加。
- 未引入自动化边界工具前，规则依赖评审和测试执行。
- 存量目录会在过渡期与新结构并存，需要修改时迁移纪律。
- 公共入口设计不当可能变成过大的 barrel 文件，仍需限制只导出稳定接口。

## 验证和复审条件

- 新模块评审必须检查独立目录、公共入口、依赖方向、数据所有权和测试边界。
- 搜索并阻止新增跨模块深层导入、业务代码进入 `shared` 和直接访问其他模块数据表。
- 当人工审查成本明显增加时，立项引入静态依赖边界检查。
- 当单个模块需要独立发布、权限隔离或团队自治时，复审是否提升为 workspace package 或独立服务。
