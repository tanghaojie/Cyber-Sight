# ADR-0020：持久化 JWT 会话并使用 LRU 读缓存

## 背景

ADR-0019 把容量为 100 的 LRU 实现成活跃 token 允许列表，导致第 101 个 token 淘汰时会话被错误撤销，进程重启也会让所有 token 失效。LRU 的目标只是降低 `auth_sessions` 的读取频率，数据库仍应持久化全部有效 token 会话。

## 决策驱动因素

- 受保护请求在缓存命中时不访问数据库。
- 缓存容量不限制有效登录会话数量。
- token 在进程重启或请求落到其他实例后可以从数据库恢复验证。
- 显式退出和用户删除具有持久撤销语义。
- 数据库不保存可直接重放的明文 JWT。

## 考虑的方案

- 纯 JWT：无需会话读取，但难以持久撤销。
- LRU 活跃允许列表：命中快，但错误地把缓存容量变成会话容量。
- 数据库 token 会话加进程内 LRU 读缓存：命中零数据库读取，未命中回源，兼顾持久化和容量边界。

## 决策

采用数据库 token 会话加 LRU 读缓存。登录签发 8 小时 HS256 JWT，并向 `auth_sessions` 写入 token 的 SHA-256 哈希、用户、过期时间、软删除和审计字段；明文 token 只返回客户端。

鉴权始终先验证 JWT 签名、issuer、audience、算法和过期时间。LRU 以 JWT `jti` 为键缓存当前用户快照，容量固定为 100；命中刷新顺序，未命中则按 token 哈希查询有效数据库会话和用户角色并回填。LRU 淘汰和进程重启不撤销 token。

退出持久撤销当前数据库会话并删除本地缓存。用户资料或角色变更只失效缓存以便重新加载；删除用户同时撤销其数据库会话。`auth_sessions.token_hash` 保持全表唯一，历史 token 标识不可复用。

## 正面结果

- 热 token 鉴权不读取数据库。
- 有效会话数量不受 100 个缓存槽限制。
- 重启与多实例冷缓存可从数据库恢复。
- 登出和用户删除的撤销状态持久化。

## 负面结果与风险

- 缓存未命中仍需要数据库查询，容量过小会降低命中率。
- 实例本地缓存无法自动感知其他实例上的撤销，陈旧项最长可持续到被淘汰或 token 过期；多实例严格即时撤销需要失效广播、共享缓存或较短缓存 TTL。
- `auth_sessions` 会累积过期和软删除记录，未来需要不影响有效会话的清理策略。
- `localStorage` token 仍需防范同源 XSS。

## 验证和复审条件

- 测试证明第 101 个 token 仅发生缓存淘汰，随后可通过持久层 loader 回填并继续有效。
- 测试覆盖缓存命中不回源、未命中回源、JWT 篡改/过期、持久退出、用户与角色变更失效。
- 引入多实例严格撤销、refresh token 或 token 管理 UI 时复审缓存一致性和数据清理策略。
