# ADR-0015：统一软删除业务唯一性约束

## 背景

ADR-0014 已用菜单编码证明：全表唯一约束会阻止软删除后复用业务自然键，而把
`is_deleted` 加入联合唯一索引又只能保留一条同身份的已删除历史。相同缺陷仍存在于
用户、角色、字典及业务关联表，必须形成一致规则，避免逐表重复踩坑。

## 决策驱动因素

- 未删除业务记录必须保持唯一，并由数据库保证并发安全。
- 软删除后允许重新创建相同业务身份，且可以保留任意数量历史记录。
- 安全标识和业务自然键必须区分，不能因统一规则降低令牌安全性。
- 迁移不得改写或删除现有业务数据。

## 考虑的方案

1. 保留各表当前约束并由仓储特殊处理：语义不一致，且无法绕过全表唯一约束。
2. 统一使用“业务键 + `is_deleted`”联合唯一索引：第二条同身份历史被再次删除时冲突。
3. 所有可复用业务身份使用 `WHERE is_deleted = false` 部分唯一索引；不可复用安全标识
   保持全表唯一。

## 决策

采用方案 3。以下身份只在未删除记录中唯一：

- `users.username`
- `users.email`
- `roles.code`
- `menus.code`
- `user_roles(user_id, role_id)`
- `role_menus(role_id, menu_id)`
- `dictionaries(type, value)`

所有索引条件统一为 `is_deleted = false`，名称使用 `*_active_unique`。关联表继续优先恢复
已有关系行，但数据库约束不再限制同一业务身份可保留的已删除历史数量。

`auth_sessions.token_hash` 是不可复用的安全标识，不属于业务自然键；即使会话软删除也
保持全表唯一。主键和未来其他不可复用外部标识同样不自动套用部分唯一索引，必须在模块
设计中说明语义。

## 正面结果

- 所有当前业务模块的软删除复用语义一致。
- 并发创建和更新仍由 PostgreSQL 原子约束。
- 多次创建、软删除同一业务身份不会因历史记录冲突。
- 会话令牌的历史唯一性不被削弱。

## 负面结果与风险

- 部分唯一索引依赖 PostgreSQL，跨数据库迁移需要等价实现。
- 恢复旧记录时若已有相同未删除身份，仍会收到唯一冲突，调用方必须明确处理。
- 回滚到全表唯一约束前必须先处理已经产生的重复历史身份。

## 验证和复审条件

Schema 测试逐项校验索引名称、列、唯一性和条件，并确认会话令牌仍为全表唯一约束。
迁移测试覆盖旧约束/索引删除及新索引创建。真实数据库回滚事务验证每类业务身份均能在
软删除后重复复用，未删除重码仍返回 `23505`。更换数据库、增加恢复功能或新增唯一业务
身份时复审。
