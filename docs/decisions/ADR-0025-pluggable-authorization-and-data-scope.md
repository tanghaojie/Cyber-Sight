# ADR-0025：可插拔功能授权与数据范围

## 背景

现有管理接口只验证会话，角色菜单关系只过滤前端导航，无法防止直接调用 API，也没有部门或行级数据范围。项目需要在保持 Fastify、Drizzle 和 PostgreSQL 轻量开发体验的同时，为以后替换策略引擎保留边界。

## 决策驱动因素

- 后端必须是安全边界，菜单可见性不能代替接口授权。
- 数据权限必须在数据库查询前形成条件，不能逐行回查或只过滤列表。
- 用户可以拥有多个角色、一个主部门和多个附属部门。
- 角色、用户和部门策略需要可配置并可继承。
- 公共资源不能被迫增加无业务含义的归属字段。
- 当前栈不应因第一版权限能力强制增加外置服务。

## 考虑的方案

1. 继续扩展 `role_menus`：简单，但菜单 ID 不是稳定后端能力标识，无法表达数据范围。
2. Node-Casbin：适合 subject/object/action 决策和角色层级，但当前 Drizzle 数据过滤仍需自研。
3. Cerbos：提供 `PlanResources` 和 Drizzle adapter，但引入独立 PDP、策略存储和部署一致性成本。
4. PostgreSQL RLS：数据库边界强，但与连接身份、事务变量、表级迁移和调试强耦合。
5. 本地 Provider 加稳定查询计划端口：满足当前需求，并允许以后增加 Cerbos adapter。

## 决策

选择方案 5。默认本地 Provider 使用项目数据库中的权限和数据策略表；功能权限使用稳定权限键，数据权限按主体、资源、动作和范围配置。业务模块把中立范围计划编译成参数化 Drizzle 条件。

第一版仅支持 allow 并集和默认拒绝，不实现 deny、角色继承或字段权限。用户直接策略、所有有效角色策略、部门直接策略和允许向下继承的祖先部门策略共同形成有效范围。角色通常是授权来源；只有业务资源确实由角色负责时才增加语义明确的角色归属字段。

公共资源不登记数据维度，只做功能权限。权限不写入 JWT，超级管理员通过显式功能权限和 `all` 数据策略获得能力。

## 正面结果

- 后端路由和数据查询形成统一、可测试的安全边界。
- 菜单和接口共享稳定权限键，但保持职责分离。
- 业务表只保存真实业务归属。
- 当前部署不增加外部服务，未来仍可接入 Cerbos。

## 负面结果与风险

- 需要维护本地策略解析器、部门闭包和每个资源的数据范围编译器。
- 用户、角色、部门和授权管理跨模块保存时需要清晰的事务或失败提示。
- allow 并集无法表达“某个用户例外拒绝”；出现真实需求时必须新增 ADR 说明 deny 冲突规则。
- `role_menus` 到权限键的迁移必须先回填再启用门禁，否则可能锁定管理员。

## 验证和复审条件

当出现跨服务统一授权、策略即代码、关系型共享资源、字段脱敏、deny、租户或外部审计要求时复审；Cerbos 是优先验证的外置 Provider。特别敏感表需要数据库纵深防御时单独评估 PostgreSQL RLS。
