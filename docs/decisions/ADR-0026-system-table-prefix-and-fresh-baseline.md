# ADR-0026：系统表前缀与全新数据库迁移基线

## 背景

脚手架已经形成十条迁移，物理表名没有统一标识其框架系统属性。维护者决定在当前仍可重建数据库的阶段统一表命名，并压缩早期演进历史，降低新项目初始化和审查迁移的成本。

## 决策驱动因素

- 从数据库对象名直接区分脚手架系统表和未来业务表。
- 新项目只需执行最终结构，不重复经历已被后续迁移撤销的中间状态。
- 保留当前软删除、审计、权限、初始数据和外键语义。
- 明确阻断把破坏性基线重置误解为无损升级。

## 考虑的方案

1. 新增一条原地重命名迁移：可保留数据，但继续携带全部历史，且不满足维护者要求的全新数据库基线。
2. 保留旧迁移并修改首条迁移：会导致已执行环境与仓库历史不一致，风险最高。
3. 用最终 Schema 重新生成单一基线，并要求全新数据库：迁移链最清晰，但旧数据库必须停用或另行迁数。

## 决策

选择方案 3。全部 14 张应用表使用 `sys_` 物理前缀，表属约束和索引同步使用 `sys_` 名称；TypeScript 导出、列、枚举和授权资源键保持语义名称。现有十条迁移及快照由一条 `0000` 最终基线取代。

新基线只面向空数据库，不包含旧表重命名、数据复制或旧 journal 兼容逻辑。任何需要保留旧库数据的部署必须另行批准数据迁移方案。

## 正面结果

- 系统表边界可见，未来业务表命名不再混淆。
- 新环境一次迁移得到最终结构和完整初始化数据。
- 删除先建后删列、会话表删除再恢复等无效历史噪声。

## 负面结果与风险

- 旧数据库不能直接升级，错误复用旧 `DATABASE_URL` 可能导致迁移被 journal 跳过或产生并存表。
- 原迁移逐步演进证据只保留在 Git 历史，不再属于当前可执行迁移链。
- 保留旧数据需要额外 ETL 和验证，不在本次范围内。

## 验证和复审条件

Schema 与迁移静态测试必须覆盖全部表名、单一 journal 和种子数据；可用时必须在全新 PostgreSQL 数据库执行基线。未来首次追加迁移后，重新进入“已执行迁移不可改写”的常规规则。
