# ADR-0011：以前端应用处理器执行全局 HTTP 错误行为

## 背景

ADR-0004 确立了 HTTP 401/404/500 由前端全局处理，但最初只通过 `window.dispatchEvent` 广播 DOM 事件，没有真正执行清会话、路由跳转或用户提示。DOM 事件也使行为依赖隐式监听顺序，不便单元测试。

## 决策驱动因素

- 401、404、500 必须有确定且可验证的用户体验。
- 共享 API Client 不应直接依赖 Pinia、Vue Router 或 Element Plus。
- 应用动作需要依赖注入并可独立测试，不依赖全局浏览器事件。

## 考虑的方案

1. 保留 DOM 自定义事件并在应用入口补监听器。耦合较松，但行为链路隐式且容易漏注册或重复注册。
2. API Client 直接导入 router、store 和 ElMessage。实现短，但产生平台循环依赖并降低测试隔离。
3. API 层暴露处理器注册接口；应用启动时注入清状态、导航和提示动作。

## 决策

采用方案 3，取代 ADR-0004 中“发布浏览器事件”的具体实现，但保留其 HTTP 状态处理边界。API Client 解析 401/404/500 后调用已注册处理器：401 清用户与导航状态、移除动态路由并跳登录；404 跳独立 404 页面；500 使用 `ElMessage` 显示响应 `err` 或安全兜底文案。

HTTP 200 的非零业务状态仍由业务模块处理，不进入全局处理器。

## 正面结果

- 全局错误有唯一、显式、可测试的执行路径。
- API Client 保持框架无关，应用入口负责组合依赖。
- 401 会同时撤销前端用户、导航缓存和动态路由，避免残留入口。

## 负面结果与风险

- 应用启动时必须先安装处理器；未安装时 API 层只返回错误数据。
- 路由跳转发生在请求响应阶段，需要避免当前已在目标错误页时重复跳转。

## 验证和复审条件

单元测试分别验证 401、404、500 动作以及其他状态不触发全局处理。当引入 SSR、多窗口或非浏览器客户端时，复审处理器注册生命周期。
