# ADR-0034：岗位与组织归属模型

## 背景

项目已有 `users`、`departments` 和 `roles` 模块。用户可以属于多个部门并拥有多个角色，但当前没有表达“用户在组织中担任什么岗位”的系统能力。岗位同时涉及组织归属和用户任职，若把岗位做成角色别名、把关系写入用户表或允许岗位部门字段与用户部门关系失配，后续会混淆授权和组织数据所有权。

## 决策驱动因素

- 岗位必须表达组织任职，而不是功能授权。
- 现有用户—部门模型允许多部门归属，岗位任职必须能被严格校验。
- 模块必须拥有自己的数据和公共接口，不能跨模块直接读写表或仓储。
- 软删除、审计字段、`sys_` 表前缀和数据库标识符规则必须与现有数据库基线一致。
- 第一版应保留岗位跨部门复用、主岗位和岗位层级等需求的后续演进空间，但不能为不明确的需求引入多余关系。

## 考虑的方案

1. **岗位作为角色**：复用角色权限关系，改动少，但会把组织称谓和安全授权混为一谈，无法表达同一角色在不同部门的任职。
2. **全局岗位 + 用户岗位多对多**：岗位不绑定部门，结构简单，但无法保证“岗位属于哪个组织上下文”，部门管理和岗位管理之间缺少明确的引用边界。
3. **岗位单部门归属 + 用户岗位多对多**：岗位定义绑定一个部门，用户通过关系表拥有多个岗位；写入时校验岗位所属部门属于用户有效部门。模型语义明确，能够复用当前部门树和用户多部门关系。
4. **岗位多部门归属 + 用户岗位关系附带部门**：表达力最大，但需要同时定义岗位—部门和用户—岗位—部门两层关系、重复一致性、移动和授权范围，超出第一版需求。

## 决策

采用方案 3：

- 新增 `system/positions` 模块，稳定模块名为 `positions`。
- `sys_positions.department_id` 为必填外键；一个岗位定义只属于一个有效部门，同部门活动岗位名称唯一。
- 新增 `sys_user_positions(user_id, position_id)` 多对多关系；关系表不复制 `department_id`，任职部门始终由岗位定义推导。
- `positions` 拥有岗位定义和用户岗位关系。`users` 通过登记的 `positions.service.ts` 协作，`positions` 通过 `departments.access.ts` 校验岗位所属部门；模块之间不能直接读写对方仓储或表。
- 用户可以无岗位或多岗位，第一版不设主岗位。用户任职有效的必要条件是：用户、岗位、岗位所属部门和关系均未软删除且启用，并且用户有该部门的有效归属。
- 岗位不参与功能权限和数据策略。第一版只登记 `positions.manage` 功能权限，不把 `positions` 登记为数据范围资源。
- 岗位删除、用户部门变更和岗位部门移动必须保护已有有效关系；部门软删除不级联删除岗位，相关岗位通过有效性查询失效并保留历史。有冲突时拒绝操作，不静默级联改写用户组织数据。

## 正面结果

- 角色继续是唯一功能授权来源，岗位不会意外扩大 API 或菜单权限。
- 部门、用户、岗位各自拥有清晰数据边界，用户多部门和多岗位都能由关系表表达。
- 岗位所属部门单一事实来源，避免在用户岗位关系中复制部门 ID 造成不一致。
- 现有部门闭包、用户部门公共访问和软删除/审计规则可以直接复用。
- 未来可在独立 ADR 中增加跨部门共享、主岗位、岗位层级或岗位数据范围，不需要现在预埋模糊字段。

## 负面结果与风险

- 用户部门调整和岗位管理之间出现跨模块校验，需要清晰的 application service 和事务边界；部门软删除与岗位采用有效性过滤保持单向依赖。
- 同一语义岗位若需要跨部门复用，第一版必须创建多个岗位定义，后续迁移到多部门模型会有数据迁移成本。
- 岗位在第一版没有数据范围；拥有 `positions.manage` 的管理员可以管理全部部门的岗位，部门级管理需求出现时必须扩展授权模型。
- 不设主岗位会使部分业务无法直接选出唯一岗位；新增 `is_primary` 前必须先定义其与主部门的约束。

## 验证和复审条件

实现已验证：

- 两张新表符合 `sys_` 前缀、审计字段、外键和活动部分唯一索引规则。
- 用户岗位关系的创建、替换、软删除和恢复不会绕过用户部门有效性。
- 岗位删除、部门归属移除和岗位部门移动不会留下失效的有效任职；部门软删除后历史岗位不会继续作为有效任职。
- 岗位权限键不会出现在角色权限、菜单运行时授权来源或数据策略主体中。

出现以下需求时复审本 ADR：同一岗位定义跨多个部门、岗位层级/继承、主岗位影响业务规则、任职历史/生效时间、部门级岗位数据权限或岗位参与授权决策。

## 实现状态

实现已落在 `apps/backend/src/foundation/modules/positions/`、`apps/frontend/src/foundation/modules/positions/` 和 `packages/api-contract/src/foundation/modules/positions/`；两张岗位表、权限和菜单种子现已合并到 `apps/backend/drizzle/foundation/0000_initial_uuidv7_foundation_schema.sql`，其主键和引用统一为 UUID。用户模块通过岗位公共服务在同一事务中替换或失效岗位关系，岗位编码未加入模型。
