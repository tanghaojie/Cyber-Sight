# ADR-0029：采用前端模块化运行时本地化

## 背景

Cyber-Sight 的运行时管理界面默认使用中文，但产品需要服务英文使用者。当前固定文案、路由标题、
动态菜单、Element Plus 文案和日期格式分散在应用壳与各系统模块中；数据库菜单只有单一
`name` 字段，用户明确要求自定义菜单保持原样且不增加数据库字段。

## 决策驱动因素

- 保留默认中文，同时让运行时界面无需刷新即可切换英文。
- 让未来业务模块能够拥有自己的翻译资源，不把领域文案集中成全局文件。
- 不修改数据库、后端和共享 API 契约。
- 严格区分代码定义的固定界面文案与用户录入数据。
- 确保默认系统菜单可翻译，但用户编辑后不被脚手架翻译覆盖。

## 考虑的方案

1. 只在应用入口维护一份全局中英文对象：实现简单，但资源所有权会随模块增长而失控。
2. 给菜单和其他数据表增加语言字段或翻译表：能支持任意数据翻译，但违背用户确认的单值
   `name` 与无数据库变更约束。
3. 使用独立前端 `localization` 模块提供机制，各业务模块拥有资源；默认菜单通过严格指纹
   识别，自定义数据原样展示：满足运行时切换和模块边界，且无需跨层变更。
4. 让后端读取 `Accept-Language` 并生成本地化错误：可以翻译服务端文案，但会扩散到所有
   路由和 API 消费方，不符合本次纯运行时前端范围。

## 决策

采用方案 3，并补充以下约束：

- 使用 Vue I18n 作为 Vue 3 运行时翻译引擎，`localization` 模块封装其全局实例和持久化。
- 支持 `zh-CN` 与 `en-US`，默认及回退语言为 `zh-CN`。
- 模块以 `*.locales.ts` 拥有自己的文案，中文和英文必须具有相同键集合。
- Element Plus、日期格式、HTML 语言和页面标题统一消费当前语言。
- 数据库菜单保持原契约。只有完整匹配类型、规范路径、组件标识和初始名称的默认菜单使用
  翻译；所有其他菜单直接显示 `name`。
- 用户录入的部门、角色、字典和其他业务数据不参与自动翻译。
- API `status` 继续是业务分支依据，前端按场景提供本地化提示，不改变后端 `err`。

## 正面结果

- 运行时界面拥有统一、可扩展的双语能力。
- 新业务模块可独立交付和审查自己的翻译资源。
- 自定义数据不被名称猜测或数据库迁移影响。
- 默认菜单、路由、面包屑和标签能够使用同一稳定标签描述。
- 后端和外部 API 消费方不承担界面语言状态。

## 负面结果与风险

- 默认菜单指纹必须随脚手架默认导航调整而同步维护。
- 用户修改默认菜单任一指纹字段后会看到其原始名称，而不再使用系统翻译。
- 前端场景化错误提示可能比后端英文 `err` 更概括；未来若需要精确双语错误，需要更细错误码
  或独立的结构化错误设计。
- 所有语言资源随首屏打包；当前仅两种语言且规模较小，暂不承担异步加载复杂度。

## 验证和复审条件

- 中英文切换覆盖固定界面、Element Plus、日期、默认菜单、标题和提示。
- 自定义菜单及其他用户数据在两种语言下保持原样。
- 类型检查能发现模块资源中的语言键缺失。
- 如果增加大量语言、需要翻译用户数据、需要服务端本地化或语言包显著影响首屏体积，复审
  资源加载和跨层协议策略。
