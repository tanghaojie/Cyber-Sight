# ADR-0038：有界授权委托

## 背景

功能权限只回答用户能否调用某类管理能力，数据策略回答该能力能作用于哪些记录。原实现允许持有 `users.manage`、`roles.manage` 或 `departments.manage` 的用户整体替换授权主体配置，却没有限制目标主体范围和可授予上限。受限管理员因此可以给自身写入 `all` 数据策略，或通过角色、部门归属取得超过自身的权限。

## 决策驱动因素

- 功能门禁、数据范围和授权委托不能互相替代。
- 管理员不得授予自身不具备的功能权限或数据覆盖范围。
- 当前配置和替换后配置都要受约束，避免通过删除、替换或上下文切换绕过。
- 本地和外部授权 Provider 必须在同一公共边界表达委托决策。

## 考虑的方案

1. 只把主体授权接口临时限制给初始超级管理员。
2. 仅把顺序 ID 改成 UUID，降低主体枚举便利性。
3. 在授权 Provider 建立有界委托决策，并让主体配置与用户角色、部门变更共同执行。

## 决策

选择方案 3。用户主体的读取和替换分别使用操作者的 `users/read` 与 `users/update` 数据范围隐藏范围外目标；所有主体的当前配置和待写入配置都必须是操作者有效权限与数据范围的子集。用户创建或更新时，角色、部门、直接用户策略及可继承策略形成的当前和目标授权上下文都执行相同子集检查。

`all` 只能由对应动作已经不受限的操作者委托；固定部门范围在展开后必须落在操作者部门范围内；依赖目标用户身份或部门的动态范围按目标最终上下文计算。无法证明子集时默认拒绝。外部 Provider 缺少委托决策实现时不得默认放行。

## 正面结果

- 阻止受限管理员给自己写入 `all` 或分配更高权限角色。
- 顺序 ID 即使可猜测，也不能绕过目标范围和委托上限。
- 授权安全边界继续位于可替换 Provider，而不是散落在前端或数据库调用中。

## 负面结果与风险

- 管理写入会增加少量授权上下文查询，换取明确的安全边界。
- 受限管理员不能编辑自己无法完整委托的高权限主体；客户端必须正确展示后端拒绝。
- 外部 Provider 需要实现新增委托接口。

## 验证和复审条件

- 后端测试覆盖范围外目标、自身 `all`、高权限角色和合法子集委托。
- 用户、角色、部门增加新的授权来源或数据资源时，必须扩展上下文比较测试。
- 如果未来引入显式授权管理员或跨租户委托，复审子集关系和目标隐藏语义。
