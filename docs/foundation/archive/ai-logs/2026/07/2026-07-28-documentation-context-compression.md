# 文档上下文压缩与统一归档

## 用户目标和约束

用户要求检查废弃、旧文档及其内容，压缩 AI 每次需要读取的 `docs/` 上下文，并设计一个默认不读取、必要时才查看的归档目录。历史资料必须保存而不是删除。

## 关键问答与确认

用户将任务标记为重要任务，未限定只处理某一种文档。按仓库规则，本次作为跨文档治理的非简单改动处理，并形成设计、ADR、实施计划和协作记录。

## AI 的重要假设

- “压缩”优先指减少默认上下文，而不是减少 Git 仓库总字节数。
- 文档是否归档以现行性、替代关系和内容权威性判断，不单纯按创建日期。
- 当前设计可以合并重复内容；已接受 ADR 的历史理由保持原意。

## 方案和执行摘要

开始时通过暂存区硬门禁，工作区为空。基线为 79 份文档、5,438 行、255,423 字节。审计识别出已取代 ADR、完成计划、完成日志，以及系统级设计和模块设计之间的重复内容。

建立统一 `docs/archive/{design,decisions,plans,ai-logs}` 和归档索引；迁移 5 份旧设计、4 份已取代 ADR、18 份完成计划和 17 份完成日志。压缩根入口、索引、系统概览、模块边界和前端应用壳，更新 `AGENTS.md` 的最小阅读协议与任务结束归档规则，并修正根 README 中已经过时的页面注册说明。

## 验证结果

- Markdown 相对链接检查：0 个断链。
- 现行/归档 ADR、设计、计划和日志的状态与目录一致。
- 当前区最终为 39 份、2,009 行、101,154 字节，较基线分别减少约 51%、63%、60%。
- 固定路由文档集由 403 行压缩为 225 行；日常任务还可按协议只选相关设计和 ADR。
- `git diff --check` 通过；未改运行时代码，因此未执行业务测试。

## 未决问题与下一步

无。后续只有在历史追溯、回归/兼容性排查或恢复旧方案时才进入归档。
