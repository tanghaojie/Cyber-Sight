# 部门树形展示协作记录

## 用户目标和约束

用户指出部门管理应使用树结构表达上下级关系，并明确要求把当前扁平列表修改为树结构展示。

## 关键问答与确认

- 诊断确认共享契约已经提供 `parentId`，后端返回全量扁平部门记录，数据能力不存在阻塞。
- 现行部门设计明确要求前端树表格，原普通表格属于首次实现和人工验收遗漏。
- 用户在诊断结论后直接授权实施树形展示。

## AI 的重要假设

- 保持后端扁平响应契约，在前端部门模块内部组树，避免不必要的跨层改动。
- 搜索命中子节点时显示祖先路径；父节点自身命中时保留完整子树，便于理解组织上下文。
- 父部门选择属于同一层级交互，同步树形化；编辑时前端排除当前节点及其后代，后端继续负责最终防环校验。

## 方案和执行摘要

更新现行部门设计后，新增模块内部树构建、搜索过滤、子树 ID 收集和树选择选项转换能力。部门列表接入 Element Plus 树表格并默认展开；父部门字段接入可搜索树选择，停用部门作为层级上下文保留但不可选。

## 验证结果

- `pnpm format`、`pnpm format:check`、`pnpm lint` 和 `git diff --check` 通过。
- `pnpm --filter @scaffold/frontend build` 在沙箱中因已知的 Vite/esbuild 目录权限限制失败，在授权环境重跑后通过；保留既有 Sass API 与重复导入警告。
- 按仓库规则未创建或运行前端自动化/浏览器测试，维护者仍需人工验收树表格和树选择交互。

## 未决问题与下一步

维护者需在浏览器中人工验收树节点展开/折叠、搜索上下文、父部门选择和窄屏布局。
