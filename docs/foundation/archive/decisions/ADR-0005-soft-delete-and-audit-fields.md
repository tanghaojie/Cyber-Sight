# ADR-0005：统一软删除与审计字段

## 背景

管理系统需要可追踪的数据生命周期，并要求所有表统一采用软删除。若各模块自行决定字段名称和过滤方式，删除数据容易意外重新出现在查询中，审计语义也会分裂。

## 决策驱动因素

- 删除可恢复且保留关联历史。
- 创建与修改责任人可追踪。
- 新模块可复用同一套 Schema 和查询约束。
- PostgreSQL 专属实现保持在基础设施层。

## 考虑的方案

1. 物理删除加独立审计日志：查询简单，但恢复和关联追踪成本高。
2. 各表按需增加软删除字段：初期灵活，但长期容易出现命名和过滤遗漏。
3. 所有持久化业务表统一生命周期字段并默认过滤：约束明确，查询需要持续遵守过滤规则。

## 决策

采用方案 3。所有业务表统一包含 `is_deleted`、`created_at`、`created_by`、`updated_at`、`updated_by`。业务查询默认只返回 `is_deleted = false`；删除仅更新 `is_deleted`、`updated_at` 和 `updated_by`。关联表和会话表同样遵守该规则。

用户原始描述中的第五个字段重复写为“更新时间”，结合审计完整性将其解释为“更新人”。字段由共享 Drizzle 列构造器统一声明，但数据库过滤必须由仓储层显式表达，不能假定 ORM 自动注入。

## 正面结果

- 表结构、迁移和审计语义统一。
- 删除数据保留，可供后续恢复和审计能力使用。
- 业务层不会直接依赖 PostgreSQL 字段实现细节。

## 负面结果与风险

- 唯一约束需要考虑已删除记录是否允许复用自然键。
- 所有读取、统计和关联查询都必须带软删除条件，遗漏会造成数据泄漏。
- 数据量增长后需要归档或清理策略。

## 验证和复审条件

Schema 测试校验所有业务表包含五个字段；仓储测试覆盖删除后查询不可见。出现法规要求物理清除、超大数据量或跨库迁移时复审本决策。
